# 配置文件更新与管理范围

## 已实现的文件更新层

`framework/file-update.c` 在 `OS.c` 之后引入，不依赖 `env.c`。
环境变量模块通过它提交 POSIX 配置变化，原有环境变量解析、启动路径选择和 Windows 注册表后端保持各自职责。

两个接口分别处理读取和提交：

- `chsrc_read_file_bytes(path, &content, &length)`：按字节读取，支持内嵌 NUL；
  返回的缓冲区额外以 NUL 结尾，调用者负责释放。
- `chsrc_update_files(ops, count, &error)`：提交一组 `FileUpdate_t`，当前仅提供 POSIX 后端。
  返回 `FileUpdate_OK`、`FileUpdate_Unchanged` 或 `FileUpdate_Failed`。
  `error` 可省略；提供时，返回的错误字符串由调用者释放。

调用者先在内存中完成全部格式检查与转换，再交付原始快照和目标内容：

```c
FileUpdate_t update = {
  .display_path = config_path,
  .norm_path = normalized_path,
  .existed = existed,
  .old_content = original,
  .old_len = original_length,
  .new_content = desired,
  .new_len = desired_length
};
FileUpdateResult_t result = chsrc_update_files (&update, 1, &error);
```

上述路径和缓冲区均由调用者持有，提交期间不能修改或释放。
文件层不识别 URL、变量名、JSON 键或 BEGIN/ENDIN 标记，也不执行包管理器更新命令。

行为约定：

1. 新旧字节相同时不写入、不备份；空批次返回 `FileUpdate_Unchanged`。
2. 已有文件可以写成空文件；不存在且目标为空时不创建文件。删除整个文件不属于此接口。
3. Dry Run 只显示待修改文件，不创建目标、父目录、备份或暂存文件。
4. 对将修改的已有文件复核旧内容，过期快照导致整批中止；全部暂存完成后才开始备份和替换。
5. 每个目标单独原子替换；后续替换失败时回滚已提交文件，并移除本批新建的目标文件。
6. 保留符号链接，修改其目标。解析到相同路径的相同更新只提交一次，矛盾的更新在提交前拒绝。
7. 保留属主、属组、权限位；新文件权限使用 `0666 & ~umask`。

当前边界：不承诺进程崩溃或断电时的多文件原子性；不锁定外部写入者，快照检查仍存在竞态窗口。
ACL、扩展属性（包括 SELinux 标签）和硬链接关系尚未保留，不能据此宣称支持所有系统配置的完整元数据迁移。
失败时可能留下本次创建的空父目录及已完成的常规备份；回滚自身失败时会保留恢复文件并提示其路径。
常规备份沿用框架的 `chsrc_backup`，其执行失败仍遵循框架现有的退出策略。

独立测试 `test/file-update.c` 不引入环境变量模块。
运行 `make test-file-update` 或 `just test-file-update`，也可通过 POSIX `make test` 和 `just test` 执行。

## 后续配置编辑层的设计

以下为后续适配器的设计约定，本次尚未修改 Debian、JSON 等 recipe 的换源行为，
也没有实现区块管理器或配置接管命令。

文件更新成功，只说明指定字节被可靠写入。配置是否选对、是否重复、是否仍指向官方源，
需要由 recipe 和格式适配器共同判断。应分开验证：

- 重复设置同一个镜像：目标字节不变。
- 镜像 A → B → A：每次都能更新选中的仓库。
- 非管理范围的内容：字节不变。
- 解析失败、归属不明或目标不唯一：在文件层提交前中止。

## Debian：官方源 + 旧版 chsrc 源 + 官方源

仅凭内容不能可靠推断来源。一个镜像 URL 既可能由旧版 chsrc 写入，也可能由用户手工添加。
“位于两个官方源之间”“属于已知镜像站”“看起来像旧模板”只能帮助列出候选，不能证明管理归属。
历史模板里的单个 `# Generated by chsrc ...` 注释也不能为任意后续内容提供结束边界。

若目标是只替换中间旧源，建议按以下顺序确定范围：

1. 已有完整、唯一且合法的 chsrc 区块：定位该区块，按 APT 格式解析并更新其中的目标 URI。
2. 专门由 chsrc 管理的独立源文件：以该文件中的明确仓库记录为范围。
3. 无标记的混合旧文件：展示候选条目，要求用户明确选择要接管的条目或先手工补上边界。
   在归属明确后完成一次迁移，之后按新边界更新。

例如，将用户选中的连续旧配置迁移为：

```text
deb https://deb.debian.org/debian trixie main

# ------ chsrc BLOCK BEGIN for Debian ------
deb https://mirror.example/debian trixie main
# ------ chsrc BLOCK ENDIN for Debian ------

deb https://deb.debian.org/debian trixie-updates main
```

以后的局部换源只修改中间区块。上下两条官方源仍然有效。
因此“更新 chsrc 管理的部分”与“使全部选定 Debian 仓库使用新镜像”是两个不同的操作范围。
若用户选择后者，就必须显式纳入对应官方条目；只追加一个 `chsrc.sources` 文件不会禁用其他源。

APT 适配器需要同时解析单行 `.list` 和 Deb822 `.sources`，在完整记录边界内定位 URI。
仓库匹配应结合归档类型（普通仓库或 security）、suite、components、`deb`/`deb-src`、
架构及签名选项；镜像 URL 是可变属性，不能单独充当稳定身份。
应保留 `Signed-By`、启用状态、其他选项与注释，不合并签名或仓库语义不同的条目。
Deb822 的 `URIs`、`Suites` 等字段可以包含多个值，`Signed-By` 还可能包含多行公钥，
都不能按“找一个 URL 的整行替换”处理。

兼容性策略建议采用“明确归属后迁移”。可以要求无标记旧配置先迁移一次，
但不宜通过忽略旧配置并追加新区块来完成换源，否则旧源仍可能继续参与更新。

## BEGIN/ENDIN 的作用和限制

可以保留维护者已有的 `BEGIN` / `ENDIN` 拼写；关键是稳定的区块标识和严格的边界检查。
空行只有排版作用，不能作为所有权标记。

支持注释的格式可使用带 recipe 标识的注释标记，并要求完整成对、不嵌套、同一标识唯一。
缺失结束标记、顺序错误、重复区块或区块内出现无法安全处理的配置时，应拒绝修改。
多个历史区块需要一次明确的迁移，不直接删除首个 BEGIN 到最后一个 ENDIN 之间的全部内容。

区块解决的是修改范围，不能替代格式校验；Debian 的签名选项、Shell 的条件块和多行字符串仍需解析。
目前的 env 模块继续按变量名和 Shell 语法工作，本次没有切换为区块覆写，也没有移除旧格式兼容逻辑。

## 不支持注释的 JSON

JSON 适配器使用结构边界确定范围。例如 recipe 明确管理 `/registry` 这个对象成员，
重复 set 时更新这个成员；其他成员保持原样，不需要 BEGIN/ENDIN 注释。
数组应使用应用已有的稳定 ID 或明确的匹配条件定位，不能依赖易变化的下标猜测旧条目。

建议保留原文及语法节点的字节位置，只替换选中值对应的片段，避免整份重新序列化造成格式噪声。
节点不存在时按 schema 创建；类型不符、重复键或匹配多个候选时拒绝猜测。
严格 JSON 不支持注释，不能插入注释标记，也不应擅自增加应用 schema 未允许的 `_chsrc` 字段。

若应用原生支持独立配置片段，可以利用其支持的文件边界；否则采用明确的结构路径。
项目遵循 NO UFO 原则，本方案不额外创建隐藏状态文件来记录归属。
没有原始值记录时，reset 只能遵循 recipe 明确规定的“恢复上游/移除指定配置”语义，不能声称恢复任意历史用户值。
